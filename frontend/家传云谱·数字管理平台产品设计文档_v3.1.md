## 第零部分：产品概述与版本规划

### 0.1 产品定位与价值主张

家传云谱是一款面向家族修谱场景的 SaaS 平台，以"低门槛数字化修谱 + 传统版式专业输出 + 世代永续续修"为核心价值，帮助家族将纸质老谱转化为可迭代的数字资产，实现家谱信息管理、内容编排、校对、排版定稿、发布归档的全流程线上化。

**核心价值主张**：
- **降低修谱门槛**：无需专业排版技能，结构化录入即可生成符合传统规范的谱书
- **保障修谱质量**：五步流程 + 多人协作 + 校对机制，兼顾效率与严谨
- **实现永续传承**：版本封存 + 多期续修 + 增量编辑，让族谱代代延续
- **AI 赋能效率**：AI 老谱 OCR 识别、逻辑冲突检测、智能校对，大幅降低人工成本（OCR 为 Spike 验证项，详见 §0.3.1）

### 0.2 目标用户画像

| 用户角色 | 典型特征 | 核心诉求 |
|----------|----------|----------|
| **族谱主编/发起人** | 家族中热心修谱的长辈或中年人，有一定文化水平，熟悉家族历史 | 高效组织协作、把控修谱质量、输出专业谱书 |
| **房头采编** | 各房支负责收集本房资料的人员，年龄跨度大，计算机水平参差 | 简单易用的数据录入工具、清晰的任务分工 |
| **校勘员** | 负责校对审核的家族文化人，对族谱内容准确性要求高 | 批量校对、疑点标注、版本对比 |
| **分支负责人** | 各房支推选的联络人，熟悉本支人员情况 | 管理本支人员信息、参与分支校对、上传本支资料 |
| **普通族人/浏览者** | 家族成员，对族谱有查阅需求，不参与编辑 | 方便查看世系、查找宗亲、了解家族历史 |
| **平台运营管理员** | 平台方运营、客服、运维人员 | 用户管理、内容风控、数据监控、售后处理 |

### 0.3 MVP 范围定义（V1.0 一期）

**一期目标**：验证核心流程跑通，支持单族谱从创建到归档的完整闭环，满足中小家族（500人以内）的首修需求。

**设计原则**：MVP 按"垂直切片"裁剪——先跑通一条最短可用路径（建谱→录人/关系→一种导出→拥有者+采编），再逐步扩入校勘双审、多版式、家族文化全量、续修与分享。MVP 不按全文规格交付，苏式排版独立 Spike 验证可行性后再决定是否纳入一期。

#### 0.3.1 MVP 核心切片（一期必做，按交付优先级排序）

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | 用户注册登录与账号管理 | 手机号验证码登录 |
| P0 | 单族谱创建与基础设置 | 族谱名、堂号、始祖、隐私设置 |
| P0 | 人物数据采集（增删改查） | 手动新增为主，批量导入Excel为辅 |
| P0 | 亲属关系管理 | 父子、配偶、出继/嗣子核心关系 |
| P0 | 人物全局搜索 | 按姓名/字号/字辈/世代快速查找定位（MVP 一期目标 500 人内，搜索为效率工具而非"万人"硬指标；大规模族谱为 V2+ 场景） |
| P0 | 谱书章节管理 | 凡例、谱序、传记富文本编辑 |
| P0 | 牒记式排版 + PDF导出 | **先上牒记式**（实现成本低），苏式垂丝独立 Spike |
| P0 | AI老谱OCR识别（Spike验证） | **Spike验证项**：MVP期间做可行性验证（拍照/上传老谱扫描件→AI识别→校对确认→入库），验证识别准确率和成本可行性。**Spike通过后正式纳入P0，未通过则降为V1.5**。不作为MVP硬性交付物 |
| P0 | 版本快照与归档 | 归档后只读封存 |
| P0 | 订阅体系 | 试用+基础年付，额度管控 |
| P1 | 协作成员管理 | **MVP仅拥有者+采编两角色**，主编/校勘/分支负责人/只读降为V1.5 |
| P1 | 逻辑冲突检测（基础版） | 父龄<子龄、断代缺失、重复人物、世代异常自动预警。**基础版仅检测不拦截（标黄提醒），V1.5增强为硬错拦截+校对门禁** |
| P1 | 世系图可视化 | 垂丝图缩放拖拽，支持折叠+分代渲染 |
| P1 | 字辈派语设置与校验 | 可存+存疑策略 |
| P1 | 附件档案管理 | 图片上传与管理 |
| P2 | 后台管理（最小集） | 用户列表+订单列表+审计日志，内容审核/敏感词降为V1.5 |
| P2 | 家族文化（最小集） | **MVP仅上家规家训+家族大事记两个Tab**，姓氏源流/堂号/相册降为V1.5 |
| P2 | 族内只读分享链接 | 拥有者生成分享链接，族人可只读浏览（无编辑），MVP末段上线 |

#### 0.3.2 MVP 简易模式（降门槛）

针对个人用户和小家族场景，提供"简易模式"选项：

| 维度 | 标准模式 | 简易模式 |
|------|---------|---------|
| 适用用户 | 专业修谱团队、大家族 | 个人、小家族（50人以内） |
| 流程 | 五步强制流程（MVP标准模式由拥有者代行校对+终审，V1.5开放全角色双审） | 跳过"校对"阶段（四步流程：项目启动→内容编排→排版定稿→发布归档），又称"快捷成谱" |
| 角色 | 拥有者+主编+采编+校勘+分支负责人+只读（V1.5全角色；MVP仅拥有者+采编） | 仅拥有者（单人操作） |
| 版式 | 牒记式（MVP）+ 苏式（Spike/V1.5） | 牒记式（预置模板，不需配置排版参数） |
| 导入 | 批量导入Excel + AI老谱OCR（Spike通过后） | 手动新增为主 |
| 可切换 | — | 可升级至标准模式 |

**切换规则**：用户创建族谱时选择模式，后续可在设置中从简易模式升级为标准模式。**不可降级**——因为标准模式下会产生审核状态、角色授权、校勘批注等流程语义数据，降级后这些数据失去含义、无法还原。升级时自动补齐校对阶段入口，已有数据全部保留。

#### 0.3.3 MVP 暂不做（Out of Scope，V1.5+ 迭代）

- 多族谱管理（一期仅支持单族谱，通过 Subscription.max_genealogy_count=1 硬限制，试用套餐限1个；基础/专业套餐可在后台配置上限，但MVP默认仍为1个）
- 多期续修功能（一期仅支持初始修谱，续修在 V1.5 上线）
  - **MVP 边界说明**：续修功能在 MVP 中仅做数据模型预留（Project 实体保留 `project_type=2` 续修类型、`base_version_id` 基准版本字段、VersionSnapshot 快照机制），前端续修相关入口（发布归档页"续修发起"Tab、版本对比功能、续修继承选项）在 MVP 中隐藏展示并标注"V1.5 上线"，不做功能开发
- **苏式垂丝排版**（独立 Spike 验证可行性后决定是否纳入一期，MVP默认仅上牒记式，Spike通过后视情况提前）
- 宝塔式、欧式分栏版式（V1.5 上线）
- **主编、校勘、分支负责人、只读角色**（MVP仅拥有者+采编，V1.5开放全角色）
- **校对双审流程**（MVP简易模式跳过校对阶段，标准模式由拥有者代行校对+终审，V1.5强制双审）
- **家族文化全量**（姓氏源流、堂号起源、家族相册三个Tab降为V1.5，MVP仅上家规家训+大事记）
- **AI老照片修复**（V1.5上线，MVP期间OCR为Spike验证项）
- **家族迁徙地图**（V1.5上线）
- **在线祭祖/云祠堂**（V1.5上线）
- **AI智能问答**（V2.0上线）
- **家族社交/宗亲圈子**（V2.0上线）
- 高级协作功能（任务分配、评论@、实时协作）
- **移动端 App 及微信小程序**（MVP仅做Web端响应式适配768px以上平板；微信小程序轻量浏览版降为V1.5）
- 族谱分享与传播机制（完整分享/族人注册浏览放 V2.0；**MVP末段上族内只读链接**，作为增长试验）
- 运营工具（优惠券、拼团、分销）
- **GEDCOM 导出**（V1.5上线，MVP仅支持PDF导出）

### 0.5 成功指标

**北极星指标**：月活跃族谱数（当月有数据变动——新增人物、修改信息、推进流程——的族谱数量）

> **v3.1.2 调整说明**：原北极星为"编排/校对中的项目数"，但产品定位是"家族人丁实时管理 + 周期性修谱"的双轨平台。仅计修谱阶段会漏掉日常人丁管理活跃用户。改为"月活跃族谱数"覆盖双轨场景——日常录入人物、推进修谱流程均计入活跃。修谱完成率仍作为子指标跟踪。

**核心指标**：
- 注册 → 首修启动转化率 ≥ 30%
- 单族谱平均人物数 ≥ 80 人
- 修谱完成率（从项目启动到发布归档）≥ 20%
- 付费转化率（试用 → 付费）≥ 10%（注：v3.0 原定 15%，但 2024 年行业年付渗透率仅 17.5%，按行业基准下调至 10% 更务实）
- 续费率 ≥ 40%
- AI老谱OCR Spike验证达标率：识别准确率 ≥ 85%（印刷体），Spike通过后纳入正式指标

### 0.6 术语表

平台业务流程采用"传统修谱术语 + 现代软件术语"双名映射，文档中以现代术语为主、传统术语为辅，便于开发团队理解业务语义。

#### 0.6.1 流程术语：现代 ↔ 传统 映射

| 现代术语（文档主用） | 传统术语（业务上下文） | 含义 |
|---------------------|----------------------|------|
| 项目启动 | 发起 | 新建修谱/续修项目，初始化项目信息、凡例、负责人 |
| 数据采集 | 采录 | 房头采编录入人物、史料、附件、亲属关系（常态化进行，非独立流程阶段） |
| 内容编排 | 编修 | 主编整合数据、规整世系、完善谱文、初审内容 |
| 校对 | 校订 | 校勘员专项勘误、批注、疑点复核、驳回整改 |
| 智能排版 | 付梓 | 智能排版+手动微调、版式锁定、生成定稿谱稿 |
| 发布归档 | 发谱归档 | 版本封存、对内对外公示、续修台账记录、流程闭环 |

#### 0.6.2 进度条命名：标准模式 vs 简易模式

> **v3.1.1 核心修正**：进度条段数 = 内部状态机步数，**不再插入非流程阶段的装饰段**。"广录族人"不再作为进度条的一段，改为工作台上的**独立行动卡**（始终可点击，跳转至信息管理-人员列表），与进度条分离。

| 命名 | 适用模式 | 进度条段数 | 段名（对应内部阶段） | 设计目的 |
|------|---------|-----------|---------------------|---------|
| **五步成谱** | 标准模式 | 5段 | 壹·立堂定源(阶段1) → 贰·协同编纂(阶段2) → 叁·三校勘误(阶段3) → 肆·付梓定稿(阶段4) → 伍·颁谱典藏(阶段5) | 仪式感营销，符合传统修谱心智 |
| **快捷成谱** | 简易模式 | 4段 | 启动(阶段1) → 编排(阶段2) → 定稿(阶段4) → 归档(阶段5)，跳过阶段3校对 | 轻量快速，明确告知"已跳过会审" |

> **"广录族人"行动卡**：工作台进度条下方设置一个独立的醒目行动卡"广录族人 →"，点击跳转至日常管理区"信息管理-人员列表"。此卡**不属于进度条**，不受 current_stage 影响，始终可见、始终可点击。它的作用是引导用户录入人员数据，而非标识流程阶段。当人物数为0时高亮提醒；人物数>0后降为常规样式。

**实现规则**：
- 标准模式下，工作台顶部展示**"五步成谱"**进度条，5段精确映射内部5个阶段（current_stage 1-5）。已完成段打勾，当前段高亮，未到达段灰色不可点击。点击已到达段可跳转对应菜单
- 简易模式下，展示**"快捷成谱"**进度条，4段精确映射内部4个阶段（跳过阶段3校对）。进度条旁标注浅灰色小字"已跳过会审，可升级为标准模式"
- 简易模式升级为标准模式后，进度条从4段变5段，补充校对段（阶段3），已有数据全部保留
- **v3.1.2 修正：current_stage → 进度条高亮段序号（barIndex）映射表**（不能直等，简易模式跳过阶段3会导致错位）：

  | 模式 | current_stage | barIndex（高亮段序号） | 说明 |
  |------|---------------|----------------------|------|
  | 标准 | 1 | 1 | 段1高亮，段2-5灰 |
  | 标准 | 2 | 2 | 段1打勾，段2高亮 |
  | 标准 | 3 | 3 | 段1-2打勾，段3高亮 |
  | 标准 | 4 | 4 | 段1-3打勾，段4高亮 |
  | 标准 | 5 | 5 | 段1-4打勾，段5高亮 |
  | 简易 | 1 | 1 | 段1高亮，段2-4灰 |
  | 简易 | 2 | 2 | 段1打勾，段2高亮 |
  | 简易 | 4 | **3** | 段1-2打勾，段3高亮（**非4**） |
  | 简易 | 5 | **4** | 段1-3打勾，段4高亮（**非5**） |

  > 开发实现：`barIndex = mapping[mode][current_stage]`，不得使用 `barIndex = current_stage`。

#### 0.6.3 核心业务概念

| 术语 | 说明 |
|------|------|
| 族谱 / Genealogy | 一个家族的完整谱系数据，包含人物、关系、章节、附件等 |
| 修谱项目 | 一次具体的修谱工作（初始修谱或某一期续修），有独立的五步流程 |
| 世系 | 家族世代相承的系统，以父子关系为主线 |
| 字辈 | 家族规定的世代命名用字，用于区分辈分 |
| 房头 | 家族的分支，通常以某一代祖先的几个儿子分别立房 |
| 续修 | 在已有谱书基础上进行增补、勘误，形成新版本 |
| 垂丝图 | 以竖线（丝）连接父子的世系图样式 |
| 牒记式 | 以人物传记条目为主体、按世系排列的谱书格式 |
| 苏式 | 苏洵创立的谱式，以世代为经、以父子为纬，垂丝连线的世系图格式 |

### 0.7 信息架构说明

为降低用户学习成本、简化侧边栏层级，前后台均采用"主菜单 + 页面内 Tab"的二级信息架构：主菜单聚焦核心任务场景，同一主题下的细分功能通过页面顶部 Tab 切换，而非散落在侧边栏中。

## 第一部分：全局统一规范（前后台通用）

### 1.1 全局布局标准

全站统一采用**左侧可折叠侧边栏 + 顶部固定导航栏 + 中间主内容区**三段式布局，前台、后台布局结构一致，仅菜单内容、配色、功能不同，降低开发、学习、维护成本。

* 侧边栏：默认展开，支持一键折叠，浏览器本地记忆状态，折叠仅显图标、悬浮展示文字
* 顶部栏：固定置顶，包含logo、侧边栏切换、全局面包屑、功能按钮、消息通知、个人中心、当前族谱常驻标识
* 主内容区：独立滚动，顶部底部不跟随滚动，自适应屏幕尺寸

### 1.2 导航通用规则

* 全站强制开启**面包屑导航**，清晰展示当前页面层级，支持点击返回上级页面
* 当前菜单自动高亮，二级菜单自动展开，未选中菜单收起
* 无权限菜单、未开通功能、过期/受限功能菜单自动隐藏，不置灰、不展示，做到界面与权限强一致
* **双区菜单可见性规则**：侧边栏分为「日常管理区」与「修谱流程区」两个视觉分区，可见性规则不同：
  - **日常管理区**（工作台、信息管理、家族文化、权限管理）：始终可见，不受修谱流程进度限制。用户随时可管理人员、维护关系、录入家族文化、管理权限，实现"实时更新人丁"的常态化管理。
  - **修谱流程区**（项目启动、内容编排、校对、智能排版、发布归档）：仅显示当前已到达及之前的阶段菜单（如当前处于"内容编排"阶段，则显示"项目启动""内容编排"两个菜单，后续阶段菜单不显示）。流程引导由**工作台顶部进度条**承担——标准模式5段精确映射内部5阶段（详见 §0.6.2），简易模式4段（跳过校对），未到达阶段显示为灰色不可点击。用户点击进度条上的已到达阶段可直接跳转。进度条下方设有"广录族人"独立行动卡引导人员录入。
  - **无修谱项目时的流程区状态**：**MVP 期间创建族谱时自动生成初始修谱项目**（始终有活跃项目），因此 MVP 不存在"无修谱项目"状态。纯日常模式（无项目时仅使用日常管理区）降为 V1.5 选项，届时在工作台提供"稍后发起修谱"选项。
* **页面内 Tab 导航**：同一主菜单下的多个功能模块通过页面顶部 Tab 栏切换，Tab 状态反映当前所处子功能，支持通过 URL 直接定位到指定 Tab

### 1.3 计费与数据通用兜底规则（全站核心）

**核心分层规则**

* **平台侧数据永久留存**：因平台运营原因（过期、欠费、冻结、降级、账号封禁）均不会主动删除用户族谱、人物、附件、版本、日志数据，仅做功能权限拦截。用户数据的删除权完全归属于用户本人。
* **用户侧删除规则**：用户主动触发的删除操作，遵循"回收站 + 软删除"二级机制（详见下方 1.3.1）。
* **基础读写拦截（分场景）**：
  - **额度用尽**：禁止新增操作（新增人物、上传附件、新建项目、新建续修），但**允许编辑已有数据**（修改人物、调整关系、编辑谱文、编辑家族文化内容）
  - **订阅过期/冻结/欠费**：进入全只读模式，禁止所有写入操作（新增、编辑、导入、上传），仅保留浏览
* **高阶功能拦截**：过期/额度用尽状态下，禁止排版定稿、禁止版式锁定、禁止PDF印刷成册导出、禁止全谱导出，仅保留单条预览、普通浏览权限
* **双重校验机制**：所有写入操作前端预校验 + 后端强校验，防篡改、防绕过
* **协作计费规则**：所有协作成员的采编、上传、修改、项目操作，均消耗**族谱创建者（租户主账号）**额度，子成员独立无额度

#### 1.3.1 用户侧数据删除机制（回收站 + 软删除）

为兼顾"用户数据自主权"与"数据安全兜底"，所有用户主动删除操作采用二级机制：

**第一级：回收站（30天可恢复）**
* 用户删除族谱、人物、附件等数据时，数据不立即物理删除，而是移入"回收站"
* 回收站保留期为 30 天，期间用户可随时恢复被删除的数据
* **额度占用规则**：回收站中的数据继续占用额度（人物占用人物额度、附件占用存储额度），**不立即释放**。仅在以下两种情形释放额度：
  - **回收站期满自动软删除**：30天期满后数据自动转为软删除，此时额度才释放（QuotaTransaction 记录 change_type=auto_purge）
  - **用户手动彻底删除**：用户在回收站中主动"彻底删除"某条数据，额度立即释放（QuotaTransaction 记录 change_type=manual_purge）
* **恢复时额度校验**：用户从回收站恢复数据时，系统校验当前剩余额度是否足够容纳恢复的数据。额度不足时拦截恢复操作，提示"额度不足，无法恢复，请先扩容或彻底删除其他回收站数据"
* 回收站中数据对正常业务不可见，仅在回收站页面可查看和恢复

**第二级：自动软删除（保留追溯）**
* 回收站期满 30 天后，数据自动标记为"已软删除"状态（`is_deleted = true`）
* 软删除数据在前台完全不可见，普通查询接口不返回
* 后台管理员可通过特殊权限查看软删除数据，用于合规审计、售后申诉等场景
* 软删除数据永久保留，不做物理删除（除非用户主动申请数据擦除并完成合规验证）

**特殊说明：族谱级联删除**
* 用户删除族谱时，该族谱下所有人物、关系、章节、附件、修谱项目、版本快照一并进入回收站
* 族谱删除后，协作成员自动失去访问权限
* 恢复族谱时，其下所有关联数据一并恢复

### 1.4 修谱核心通用规则（含五步流程+续修迭代）

平台严格遵循传统正统修谱范式，固定**项目启动→内容编排→校对→智能排版→发布归档**五步闭环递进流程，**禁止越级推进、支持合规回退**，同时支持族谱终身存续、N期永续续修迭代。

> **v3.1.1 核心决议**：v3.0 双区融合架构将"数据采集"从流程阶段升级为日常管理区的常态化功能（"信息管理"菜单）。内部状态机从原六步调整为五步。"数据采集"不再作为独立流程阶段。进度条不再插入"广录族人"装饰段，改为工作台独立行动卡（详见 §0.6.2）。

> **内部流程阶段名 ↔ 前台菜单名映射**（v3.1.1 五步流程）：
> 
> | 内部流程阶段 | 前台侧边栏菜单名 | 所属区域 |
> |-------------|----------------|---------|
> | 阶段 1：项目启动 | 项目启动 | 修谱流程区 |
> | 阶段 2：内容编排 | 内容编排 | 修谱流程区 |
> | 阶段 3：校对 | 校对（人员列表/校对邀请/审核结果） | 修谱流程区 |
> | 阶段 4：智能排版 | 智能排版 | 修谱流程区 |
> | 阶段 5：发布归档 | 发布归档 | 修谱流程区 |
> 
> 注：内部状态机、数据库字段（current_stage）、权限矩阵中仍使用内部阶段名；前台 UI、侧边栏、页面标题、用户可见文案统一使用前台菜单名。"数据采集"作为常态化功能归属日常管理区的"信息管理"菜单，不作为流程阶段。

> 以下"传统术语 → 现代术语"的映射贯穿全文，后续章节统一使用现代术语。

* 族谱主体唯一：单个族谱永久存续，不重复创建，所有初始修谱、续修项目均挂靠同一族谱，一脉相承
* 版本强隔离：历史定稿版本永久封存只读、不可篡改、不可覆盖；新版续修数据独立编辑、独立流程、独立存档
* 续修继承规则（v3.1.3 修正）：新建续修时**不从快照恢复人物/关系**——活数据始终是同一套（genealogy_id 下的 Person/Relationship 表）。续修继承的是**项目级数据**（章节内容从快照复制为新一期初始章节、版式参数继承），人物继续使用活数据。通过增补清单对比活数据与上一归档快照的差异，主编逐项确认纳入本期谱书的范围

**五步流程回退规则**

* 发布归档状态（阶段5）：不可回退，永久封存，仅可新建下一期续修
* 智能排版状态（阶段4）：仅可回退至【校对】（阶段3），回退自动解锁版式、重置定稿状态、清空固化页码目录
* 校对状态（阶段3）：可驳回回退至【内容编排】（阶段2），自动生成驳回台账与批量批注，标记待整改内容
* 内容编排状态（阶段2）：可回退至【项目启动】（阶段1），保留已采编数据不清空，仅解锁编辑权限
* 项目启动（阶段1）：自由编辑，无流程锁限制
* 回退权限限制：仅拥有者、主编可操作流程回退，校勘、采编、分支负责人无回退权限

**流程锁 vs 日常可写规则**（v3.1.1 新增，解决双区架构下的数据一致性）

> 核心原则：**流程锁只锁项目级数据，不锁族谱级活数据。**

| 流程阶段 | 项目级数据（章节、排版参数、凡例） | 族谱级活数据（人物、关系） | 说明 |
|----------|----------------------------------|--------------------------|------|
| 项目启动 | 可读写 | 可读写 | 全开放 |
| 内容编排 | 可读写 | 可读写 | 全开放 |
| 校对 | **锁定**（不可编辑） | **可读写**（日常管理区不受影响） | 采编仍可通过信息管理修改人物。**v3.1.4 核心规则：current_stage ∈ {3,4} 时，任何对已标记 review_status=1（通过）的人物的修改，系统自动将其 review_status 重置为 0（未审核）**。校勘员在校对-人员列表中看到的是活数据当前状态。MVP 不设"项目级人物快照"——校对直接对活数据进行，通过 review_status 跟踪校对进度。如需冻结人物数据供校对，主编可手动"快照锁定"（高级功能，V1.5） |
| 智能排版 | **锁定**（仅可微调版式参数） | **可读写** | 排版基于活数据生成。**v3.1.4 门禁：排版期改人/改关系触发 review_status 重置（与校对期一致，current_stage ∈ {3,4}）。layout_dirty=1→禁止导出。标准模式路径 A/B 均须回校对终审；简易模式无校对菜单，改为排版页内一键确认（批量置 review_status=1）** |
| 发布归档后 | 只读封存 | **可读写**（活数据继续演进） | 归档的是 VersionSnapshot 全量快照，活数据不受影响。新增/修改的人物标记 is_changed_since_archive=1，供续修增补清单使用 |

**额度规则补充**（v3.1.1 新增）：
* 日常管理区新增人物**始终消耗额度**，无论是否有活跃修谱项目
* 归档后日常新增的人物也消耗额度（活数据在增长）
* 额度用尽时，日常管理区也禁止新增人物（但不禁止编辑已有数据）
* 这意味着"归档后日常增丁"也受额度管控，拥有者需及时扩容

**校对终审放行标准**

* 系统自动判定：项目内所有人物、章节、谱文、附件无「待校对、待整改、存疑未处理」状态（即所有人物 review_status 不为 0/3）
* **review_status 重置规则**（v3.1.2 新增，v3.1.4 扩大作用域至排版阶段）：
  * **触发条件**：当存在活跃修谱项目且 `current_stage ∈ {3, 4}`（校对或排版阶段）时，通过日常管理区"信息管理"对人物/关系的修改均触发重置（v3.1.3 仅限校对阶段→v3.1.4 扩展至排版阶段，防止排版期改人绕审）
  * **人物字段修改**：任何对已标记 review_status=1（通过）的人物的修改，系统自动将其 review_status 重置为 0（未审核）
  * **关系修改的关联重置**（v3.1.3 新增）：修改 Relationship（增删改关系——如改父、加配偶、出继等）时，系统自动将**该关系的 from_person 和 to_person 的 review_status 重置为 0**，因为关系变更影响世系结构，关联人物需重新校对
  * **新增人物默认状态**：校对/排版阶段中通过日常管理区新增的人物，review_status 默认为 0（未审核），需校勘员/拥有者校对后方可终审
  * 终审时系统校验全量人物的 review_status——若存在 review_status=0（未审核）或 review_status=3（待整改）的人物（存疑归档 review_status=2 除外），终审将被拦截，需重新校对后方可放行
* **简易模式 review_status 处理**（v3.1.3 新增，v3.1.5 补充排版期处理）：
  * **推进排版时**：简易模式跳过校对阶段（阶段3），推进至智能排版（阶段4）时，系统自动将全量人物的 review_status 批量置为 1（通过），视为"拥有者一并代行校对确认"
  * **排版期改人处理**（v3.1.5 新增）：简易模式排版期改人/改关系同样触发 review_status 重置为 0，layout_dirty=1 禁止导出。但因简易模式无校对菜单，**不要求"回校对菜单终审"**，改为：排版页面弹出**"活数据已变更"确认弹窗**，拥有者点击"确认纳入"后系统再次批量将变更人物 review_status 置为 1（等同路径 A 的终审效果，但操作入口在排版页内，不跳转校对菜单）。弹窗中展示变更人物列表，支持逐条查看
  * 若后续升级为标准模式，回退至校对阶段时 review_status 保持 1 不回退，拥有者可逐条复核或直接终审
* 支持行业合规容错：主编可手动标记**存疑归档**（单项目内存疑人物数 ≤ 总人物数的 5%，且每条必须填写存疑原因与考证备注）
* 终审双保险：系统校验通过 + 主编手动终审确认，方可进入智能排版环节，禁止校勘员单人放行
* 存疑标记在后续续修中默认继承，鼓励在续修阶段核实修正

**逻辑冲突检测规则**（v3.1 新增，P1 基础版）

* 系统在校对阶段自动执行全量逻辑冲突检测，生成冲突检测报告
* **MVP 基础版（P1）：仅检测不拦截**——检测结果标黄提醒，不阻断终审放行
* **V1.5 增强版：硬错拦截 + 校对门禁**——硬错必须处理后方可终审放行
* 检测维度：
  - **年代冲突**：父龄<子龄、生卒年与世代矛盾、人物生卒年与历史事件矛盾
  - **断代缺失**：世代跳跃（如第5代直系子嗣直接跳到第7代）、关键人物无父关系
  - **重复人物**：姓名+世代+生卒年高度匹配的疑似重复人物
  - **关系异常**：性别与关系冲突（如父亲性别为女）、多人同时为生父、配偶为直系血亲
  - **字辈不匹配**：人物字辈与字辈诗不匹配（标记存疑，不拦截）
* 检测结果以列表形式展示，支持逐条确认、标记待整改、标记存疑

### 1.5 全局通用交互兜底规则

* **空状态兜底**：所有列表无数据时展示标准空状态文案+图标，隐藏筛选、批量操作按钮，无空白页面
* **加载状态兜底**：所有接口请求、页面刷新、文件加载展示统一loading状态，防止重复点击、重复提交
* **报错兜底**：接口失败、网络异常、权限失效统一友好报错提示，记录前端错误日志，不白屏、不崩溃
* **二次确认兜底**：删除、流程推进、流程回退、版式锁定、族谱删除等高风险操作统一二次弹窗确认
* **文件资源兜底**：图片、附件加载失败展示默认占位图，超大文件分片上传、断点续传、超时重试
* **防重复提交**：所有表单提交、数据写入操作1秒防抖锁定，防止重复创建、重复录入数据

### 1.6 全局多人协作锁机制

* 同一人物、同一章节、同一谱文、同一家族大事记、同一家规家训条目**单人独占编辑锁**，A用户编辑中，B用户仅可查看、不可编辑，防止数据覆盖
* 编辑超时自动释锁：无操作5分钟自动释放编辑权限，避免页面卡死占用锁
* 锁状态实时提示：页面展示「当前正在编辑人员」弹窗提示，协作透明无冲突
* 心跳检测：编辑页面每 30 秒向服务端发送心跳续租，网络断开超过 60 秒自动释锁
* 强制接管：族谱拥有者或主编可强制释放他人编辑锁，操作记入审计日志

> **v3.1.2 ER 图修正**：Person 和 Relationship 直接挂在 Genealogy 下（族谱级活数据），**不经过 Project**。Project 仅关联 Chapter（章节内容为项目级产物）和 VersionSnapshot（归档快照）。原图将 Person/Relationship 画在 Project 下，与 v3.1.1 数据模型决议矛盾，现修正。

**关系说明**：
* 一个租户（即一个付费账号）可拥有多个族谱
* 一个族谱下可有多个修谱项目（初始修谱 + 多期续修）
* **人物、亲属关系为族谱级活数据**（归属 genealogy_id），不归属具体修谱项目。这是 v3.1.1 的核心架构决议：活数据始终挂在族谱上，任何时候都可读写，与修谱流程解耦
* 谱书章节（Chapter）归属到修谱项目（project_id），因为章节内容（谱序、凡例、传记等）是项目级产物，每次修谱独立编写
* 家族大事记、家规家训归属到族谱级别（非项目级别），因为它们是跨版本累积的文化内容
* **版本隔离通过 VersionSnapshot 实现**：发布归档时将当前族谱活数据全量快照写入 VersionSnapshot，此后活数据继续可写，但快照永久只读。续修时不"恢复数据"——工作面始终是族谱级活数据，续修通过"增补清单"机制将活数据与上一归档快照对比，生成新增/修改/删除清单供主编逐项确认纳入
* **流程锁不影响活数据**：修谱流程中的"校对锁定""排版锁定"仅锁项目级数据（章节、排版参数），不锁族谱级活数据（人物、关系）。即当 `current_stage ∈ {3, 4}`（校对或排版）时，采编仍可通过"信息管理"修改人物——但**修改已通过校对的人物会重置其 review_status 为未审核**（详见 §1.4 流程锁矩阵），MVP 不设项目级人物快照

**约束**：仅支持 INSERT，不支持 UPDATE 和 DELETE（数据库层面禁止）

#### 1.7.18 实体关系补充说明

**版本快照范围定义**（v3.1.3 修正：快照不再含"项目的全部人物"——人物是族谱级活数据，不挂项目）：

版本快照在发布归档时一次性生成，包含以下数据：
* **族谱级活数据全量序列化**：当前族谱的全部 Person 和 Relationship 记录（全量快照，非项目级——活数据挂在 genealogy_id 上，快照只是冻结某一时刻的副本）
* **项目级数据**：当前项目的谱书章节（含凡例、谱序、传记等 Chapter 记录）、排版参数（版式类型、版式配置、页码目录、总页数）
* **族谱级文化数据**：家族大事记、家规家训（全量，非增量）
* **附件清单**：当前项目关联的全部附件ID和元信息（不含文件二进制，仅记录引用关系）

**快照存储策略**（v3.1新增）：万人以上族谱的快照采用分片压缩存储（每1000人一个JSON分片文件，gzip压缩），`data_snapshot_path` 指向分片索引文件，避免单个超大文件影响读写性能。

> **v3.1.3 续修不"恢复数据"**：续修时**不从快照恢复人物/关系**——活数据始终是同一套（genealogy_id 下的 Person/Relationship 表），续修只新建 Project + 继承章节（Chapter 从快照复制为新一期初始章节），人物继续使用活数据。增补清单的"确认纳入"通过 RenewalItem 表的 `decision` 字段实现（详见 §1.7.19），**不是新建 Person 行**。

**续修增补清单机制**（v3.1新增，v3.1.3 修正，v3.1.4 补全数据模型）：
* Person 实体的 `is_changed_since_archive` 字段标记归档后的变更状态（0=未变更，1=新增，2=修改，3=已删除——v3.1.3 新增：归档后软删除的人物标记为3，进入增补清单的"删除"分区，供主编确认是否在续修谱书中保留历史记录或移除）
* 发起续修时，系统查询 `is_changed_since_archive != 0` 的人物列表，自动生成 RenewalItem 记录（每条对应一个变更人物），主编逐项确认是否纳入本次续修谱书
* 确认纳入仅影响本期谱书的收录范围，**不新建或复制 Person 行**
* 确认完成后，系统将已纳入人物的 `is_changed_since_archive` 重置为 0（清零变更标记），开始新一期修谱流程
* **未纳入行为**（v3.1.4 新增）：未纳入（`RenewalItem.decision=2`）的人物**不进入本期谱书排版**，但其活数据行保留在族谱中不受影响。未纳入的变更标记**不清零**——下期续修时该人物仍会出现在增补清单中（除非主编在期间通过日常管理将其 is_changed_since_archive 手动清零）。这是设计意图：未纳入意味着"本期暂不收录"，不代表变更已消解

#### 1.7.19 续修增补条目（RenewalItem）（v3.1.4 新增）

续修增补条目是**项目级关联表**，记录某一期续修项目中每个变更人物的纳入决策。挂在 Project 上，不挂 Person 活数据。

| 字段名 | 数据类型 | 必填 | 说明 |
|--------|----------|------|------|
| id | bigint | 是 | 主键，自增 |
| project_id | bigint | 是 | 所属续修项目ID |
| person_id | bigint | 是 | 关联的活数据人物ID（不复制人物数据，仅引用） |
| genealogy_id | bigint | 是 | 冗余族谱ID，便于查询 |
| change_type | tinyint | 是 | 变更类型：1=新增，2=修改，3=已删除（与 Person.is_changed_since_archive 值对应） |
| decision | tinyint | 是 | 主编决策：0=待确认（默认），1=纳入本期谱书，2=排除本期谱书 |
| exclude_reason | varchar(256) | 否 | 排除原因（decision=2 时填写，如"信息不确定""本支暂不收录"） |
| reviewed_by | bigint | 否 | 决策人用户ID |
| reviewed_at | datetime | 否 | 决策时间 |
| created_at | datetime | 是 | 创建时间（续修发起时自动生成） |

**索引建议**：`(project_id, decision)`、`(genealogy_id, person_id)`、`(project_id, change_type)`

**排版过滤规则**（v3.1.4 新增，v3.1.5 补充首修例外）：
* **首修项目**（project_type=1，无上一期归档快照、无 RenewalItem 记录）：排版拉取**族谱全部有效活数据人物**（is_deleted=0），不经过 RenewalItem 过滤——首修没有"增补"概念，所有已录入人物均应进入谱书
* **续修项目**（project_type=2，有 RenewalItem 记录）：智能排版拉取活数据时，**仅包含当前项目 RenewalItem.decision=1 的人物**（纳入）+ 上一期归档快照中已存在且无 RenewalItem 记录的人物（未变更，默认纳入）
* RenewalItem.decision=2（排除）的人物**不出现在本期谱书排版中**
* decision=0（待确认）的人物也**不进入排版**——主编必须逐条决策后方可推进排版

> **设计说明**：RenewalItem 挂在 Project 上而非 Person 活数据上，是因为"是否纳入本期谱书"是项目级业务决策，不是人物属性。同一人物在第一期续修中可能被排除，在第二期中可能被纳入，这是独立的决策。

### 1.8 隐私与脱敏统一规则

本节统一定义隐私和脱敏规则，其他章节引用此节，避免规则分散。

#### 1.8.1 族谱隐私模式（Genealogy.privacy_mode）

| privacy_mode 值 | 模式名称 | 含义 |
|-----------------|----------|------|
| 1 | 完全私有 | 仅拥有者、协作成员可访问（需登录+Collaborator关联） |
| 2 | 族内可见 | 拥有者生成"族内浏览链接"，持有链接的族人可只读浏览（不可编辑） |
| 3 | 全网公开 | 任何人无需登录即可浏览公开内容（在世人物仍脱敏） |

#### 1.8.2 在世人物脱敏规则（Genealogy.living_desensitize）

| living_desensitize 值 | 级别名称 | 脱敏字段 | 适用场景 |
|----------------------|----------|----------|----------|
| 1 | 严格脱敏 | 隐藏生卒月日，仅显示名讳+享年范围（如"享年七十有余"） | 默认值，保护在世人物隐私 |
| 2 | 中度脱敏 | 隐藏生卒完整日期，仅显示生卒年份 | 拥有者可手动调低 |
| 3 | 完整显示 | 显示完整生卒日期 | 仅拥有者自己查看时生效，其他角色仍按脱敏规则 |

**脱敏触发条件**：当 Person.is_alive = 1（在世）时，所有展示场景（世系图、人物详情、PDF导出、批量列表）均按 living_desensitize 级别脱敏。已故人物（is_alive=0）不受脱敏限制。

**脱敏角色判定**：
* 拥有者（owner）查看时，living_desensitize 不生效（自己可看完整数据）
* 协作成员查看时，按 living_desensitize 级别脱敏
* 公开浏览者查看时，始终按最严格级别（1）脱敏，无论族谱设置

**在世状态辅助判定**（v3.1新增）：
* 当人物 `is_alive = 1` 且 `birth_date` 推算年龄超过 120 岁时，系统在人物详情页提示"该人物年龄已超过120岁，请确认是否需要标记为已故"
* 此提示为辅助提醒，不自动修改 `is_alive` 字段，由用户自行确认

#### 1.8.3 人物隐私级别（Person.privacy_level）

| privacy_level 值 | 级别名称 | 可见范围 |
|-----------------|----------|----------|
| 1 | 公开 | 所有可访问该族谱的用户均可见（含公开浏览者） |
| 2 | 族内可见 | 仅拥有者和协作成员可见 |
| 3 | 私密 | 仅拥有者可见，协作成员不可见 |

#### 1.8.4 家族相册可见范围

家族相册中每张照片通过 Attachment.metadata 中的 `privacy_level` 字段控制：
* `privacy_level = 1`（公开）：所有可访问族谱的用户可见
* `privacy_level = 2`（族内）：仅拥有者和协作成员可见
* `privacy_level = 3`（私密）：仅拥有者可见

#### 1.8.5 隐私规则优先级

当多级隐私规则同时生效时，按**最严格规则优先**：
1. 人物 privacy_level = 3（私密）→ 仅拥有者可见，忽略其他规则
2. 人物 is_alive = 1（在世）→ 按脱敏规则处理
3. 族谱 privacy_mode = 1（完全私有）→ 仅协作成员可见
4. 以上均不触发时，按各内容默认可见性展示

#### 1.8.6 族内分享链接安全规则（v3.1新增）

* 分享链接由拥有者生成，包含不可猜测的随机 token
* 链接有效期默认 90 天，拥有者可自定义有效期（7天/30天/90天/永久）
* 拥有者可随时撤销分享链接，撤销后链接立即失效
* 分享链接仅授予只读浏览权限，不可编辑、不可导出
* 在世人物信息按脱敏规则展示，不受拥有者查看权限影响
* 分享链接访问记录留存审计日志

### 1.11 AI老谱OCR识别规格（v3.1新增）

#### 1.11.1 功能定位

AI老谱OCR识别是家传云谱的核心差异化功能，通过AI技术将纸质老谱快速数字化，大幅降低人工录入成本。

> **Spike 状态说明**：此功能在 MVP 中作为 Spike 验证项，需在 MVP 开发周期内完成可行性验证（识别准确率、处理耗时、API 成本）。Spike 通过后正式纳入 P0 交付；未通过则降为 V1.5。以下规格为 Spike 验证目标。

#### 1.11.2 识别能力

| 能力项 | 说明 |
|--------|------|
| 支持版式 | 竖排刻版、竖排手写、横排印刷、混排 |
| 支持字体 | 繁体字、异体字、刻版字、手写行楷 |
| 识别内容 | 人物姓名（讳/字/号）、世代、生卒年月、籍贯、传记、世系关系 |
| 识别准确率 | 印刷体 ≥ 95%，手写体 ≥ 85%（基于清晰扫描件） |
| 结构化输出 | 识别结果自动映射到 Person 实体字段，支持人工校对确认后入库 |
| 置信度标注 | 每个识别字段标注置信度（高/中/低），低置信度字段标黄提醒人工复核 |

#### 1.11.3 使用流程

```
上传老谱扫描件/拍照
  → AI识别引擎处理（预计10-30秒/页）
  → 展示识别结果（左侧原图+右侧结构化字段）
  → 用户逐字段校对确认/修改
  → 确认入库（自动创建Person记录+Relationship记录）
  → 低置信度字段自动标记review_status=2（存疑）
```

#### 1.11.4 计费规则

* OCR识别次数独立计入套餐额度（试用5次/月，基础50次/月，专业无限）
* 单次识别按"页"计算，一页老谱识别计为1次
* 识别失败不计入次数
* 超出套餐次数时拦截使用，提示购买扩容包

#### 1.11.5 性能要求

* 单页识别处理时间 ≤ 30秒
* 支持批量上传（单次最多20页），排队处理
* 识别结果缓存 7 天，期间可反复查看和修改
* 原始扫描件永久保留在附件中，关联到对应修谱项目

## 第三部分：前台用户端设计规范

### 3.1 前台整体定位

面向所有注册用户，支持「创建族谱、数据采集、多人协作、世系展示、版本管理、附件归档、订阅续费、额度管控、排版定稿与发布归档」，适配年费订阅、额度管控、五步修谱流程的完整业务体系，权限、流程、商业化规则形成业务闭环。

### 3.2 前台全局UI布局（与后台统一）

* 左侧：可折叠侧边菜单（家谱古风简约配色）
* 顶部：Logo+菜单折叠按钮+面包屑+消息通知+个人中心+当前族谱常驻名称标识
* 中间：自适应主内容区

### 3.3 前台侧边栏菜单结构

**设计原则**：单族谱菜单采用**双区融合架构**——「日常管理区」按功能划分菜单，承担家族人丁实时管理与文化维护的常态化职责；「修谱流程区」按五步流程阶段排列，承担修谱项目的阶段推进。用户既能随时管理人员和关系（不依赖修谱项目是否启动），又能在发起修谱时按流程推进完成谱书编纂。

> **双区设计理念**：家传云谱不仅是"修一次谱就结束"的项目工具，更是"家族人丁实时管理"的长期平台。日常管理区的菜单始终可见、随时可用；修谱流程区的菜单按进度可见性规则逐步展示，与进度条联动引导用户按阶段推进。两区共存于同一侧边栏，通过视觉分区区分。
>
> **初次修谱入门路径**：创建族谱后自动生成初始修谱项目（默认处于"项目启动"阶段），工作台同时展示修谱进度条与人丁统计。用户通过「信息管理」菜单随时录入人员（不被流程阶段锁住），录入完成后在「项目启动」页配置凡例与团队，再推进至内容编排，正式进入修谱流程。**MVP 不支持"无项目纯日常"路径**——创建族谱即自动建项目，纯日常模式降为 V1.5 选项。

菜单分层规则：全局固定一级菜单 + 进入族谱后动态切换专属一级菜单，退出族谱自动还原全局菜单，杜绝多族谱场景菜单混淆。

**全局菜单（未进入族谱时）**：
1. **首页工作台**
2. **我的族谱** —— 全部族谱列表 + 创建族谱弹窗
3. **会员订阅中心** —— （点击展开二级：我的套餐 / 购买续费 / 额度流水 / 我的订单）
4. **个人中心** —— （点击展开二级：账号信息 / 修改密码 / 消息通知）

**单族谱菜单（进入族谱后）——双区融合结构**：

**区域一：日常管理区（始终可见，不依赖修谱项目状态）**

> **双区融合 vs 纯流程导向的改进**：v3.0 将原"数据采集"从流程阶段升级为常态化的"信息管理"一级菜单（含人员列表、关系图谱、字辈列表三个子菜单），使人丁数据管理不依赖修谱项目状态——用户随时可以新增人员、维护关系、更新字辈，实现"实时更新人丁"的产品理念。原"质量审核"更名为"校对"，新增"校对邀请"子菜单支持协同校对（邀请分支负责人参与校对），"审核结果"整合原"疑点台账"与"审核记录"及逻辑冲突检测。原"设置与协作"更名为"权限管理"，新增"分支负责"子菜单管理各分支负责人。原"排版定稿"更名为"智能排版"。原"族谱总览"更名为"工作台"，强化实时人丁统计与家族动态展示。修谱流程区仅显示已到达及之前的阶段菜单，未到达阶段不显示；流程引导由工作台顶部进度条承担（标准模式=五步成谱，简易模式=快捷成谱，详见 §0.6.2）。
>
> **v3.1.1 变更**：内部状态机从六步调整为五步（移除"数据采集"作为流程阶段），所有回退规则、current_stage 字段值、阶段编号全部对齐为五步。进度条段数与内部阶段数严格一一对应。

### 3.4 前台逐页面功能

#### 前台页面 01：首页工作台

**布局**：顶部状态卡片 + 中部门谱快捷入口 + 底部动态记录

**核心展示内容**：

* 账号状态：试用中/正式订阅/已过期、到期倒计时
* 额度统计：已用人物/总人物、已用存储/总存储、AI OCR剩余次数、剩余额度提示
* 数据卡片：我的族谱数量、总人物数、附件数量、修谱项目数、续修项目数量
* 快捷操作：创建新族谱、进入最近编辑族谱、新建续修项目、购买套餐、查看额度流水
* 最新动态：近期新增人物、上传附件、版本保存、成员加入、续修项目创建记录

**交互限制**：额度不足、订阅过期时，首页展示醒目续费/扩容引导横幅，隐藏所有新建、续修、定稿、高阶导出功能入口，仅保留阅览权限。

#### 前台页面 02：我的族谱

**布局**：顶部筛选+【创建族谱】弹窗按钮 + 卡片式族谱列表 + 分页 + 回收站入口

**功能说明**：移除独立创建族谱页面，统一为全局模态弹窗，一次性完成基础信息、堂号、始祖、隐私权限配置。

**核心功能**：
* 展示当前账号**自建族谱**与**以成员身份加入的族谱**（v3.1.7 候选）：名称、堂号、始祖、创建时间、公开状态、人物总数、修谱/续修项目数；成员谱卡片标注「成员 · 只读」
* 搜索/筛选族谱、编辑族谱基础信息、切换公开/私有状态（**仅自建/拥有者**；成员谱无编辑/删除）
* **邀请码加入**（v3.1.7 候选）：顶部「邀请码加入」弹窗；加入成员谱**不占**自建族谱数量上限；详见族谱成员专题 §7.2
* 删除族谱（二次强确认，移入回收站，30天内可恢复）
* 回收站入口：查看已删除族谱、恢复族谱、彻底删除（需二次验证）
* 弹窗新建族谱：订阅/额度校验通过方可创建，创建成功自动生成空族谱+默认初始修谱项目+成员邀请码
* 点击族谱卡片进入工作台

**回收站规则**：
* 删除族谱后数据保留 30 天，期间可全额恢复
* 30天后自动软删除，前台不可见，后台保留合规追溯
* 删除族谱后人物额度、存储额度立即返还
* 彻底删除操作需手机验证码二次确认，且删除后不可恢复

**拦截规则**：订阅过期、人物额度用尽，隐藏新建族谱按钮，仅可查看、管理已有族谱。

#### 前台页面 03：工作台（日常管理区首屏）

**布局**：族谱信息卡片 + 人丁实时统计 + 各世人丁分布 + 修谱流程进度条 + 家族动态流 + 快捷操作

**展示**：族谱基础信息、总人物数、各世人丁分布、章节数、附件数、家族大事记数、家族相册照片数、协作成员数、当前修谱项目状态与所处阶段、历史续修批次记录、各批次定稿时间

**人丁实时统计**：以数据卡片形式展示家族人丁总数、本月新增人数、各世人丁分布柱状图、实时更新状态指示器。突出"不但是修谱，更是家族人丁实时管理"的产品理念。

**进度条**：页面顶部横贯一个进度条，根据模式不同展示不同样式（仅当存在活跃修谱项目时显示）：
- **标准模式**：展示"五步成谱"进度条，5段精确映射内部5阶段（壹·立堂定源→贰·协同编纂→叁·三校勘误→肆·付梓定稿→伍·颁谱典藏）
- **简易模式**：展示"快捷成谱"进度条，4段（启动→编排→定稿→归档），跳过校对。进度条旁标注浅灰色小字"已跳过会审，可升级为标准模式"
- 已完成阶段打勾，当前阶段高亮，未到达阶段灰色不可点击。点击任一已到达阶段可直接跳转对应菜单页面
- **进度条下方"广录族人"行动卡**：独立于进度条，始终可见，点击跳转至信息管理-人员列表。人物数为0时高亮提醒

> 映射关系详见 §0.6.2 进度条命名规则。

**家族动态流**：以时间轴形式展示近期家族动态——新增人物、添丁记录、信息更新、校对提交、文化录入、AI OCR识别等，支持按类型筛选。实时反映家族人丁变动与协作动态。

**首次进入引导**：
- **MVP 默认路径**（有初始修谱项目）：创建族谱时自动生成初始修谱项目，进度条停在第1段"项目启动"，人丁统计显示0人，"广录族人"行动卡高亮提醒。用户通过行动卡跳转至信息管理-人员列表录入人员，录完后推进流程
- **项目归档后**：进度条全部完成打勾，"广录族人"行动卡降为常规样式，活数据继续演进（新增人物标记 is_changed_since_archive=1），待 V1.5 续修功能上线后可发起下一期
- **纯日常模式**（V1.5 选项）：届时支持创建族谱时不自动建项目，工作台进度条区域替换为"发起修谱"引导卡片，用户可自由使用日常管理功能

**快捷入口**：新增人物、打开世系图、新增家规、管理成员、发起修谱（无活跃项目时）/新建续修（有归档版本时）、AI老谱OCR识别

**页面定位**：进入族谱后的首屏，承担"人丁概览 + 流程导航 + 实时动态"三重角色，用户从此处直观感知家族人丁状况与修谱进度并分流到各功能页面。

#### 前台页面 04：项目启动（阶段 1）

**页面定位**：新建修谱/续修项目的初始化入口，配置项目基础信息、凡例、团队。

**页面结构**：顶部 Tab 栏切换三个子模块

**Tab 1：项目信息**
* 功能：项目名称、修谱年份（干支+公元）、项目类型（初始修谱/续修）、基准版本选择（续修时）
* 说明：新建项目，初始化项目基础信息

**Tab 2：凡例编写**
* 功能：富文本编辑器，编写修谱凡例（修谱说明、体例、范围说明）
* 说明：凡例将作为谱书的开篇章节，后续可在"内容编排"阶段继续修改。**凡例的权威存储为 Chapter 实体（chapter_type=fanli）**，项目启动页编辑凡例时自动同步创建/更新对应 Chapter 记录，Project.fanli 字段仅做缓存快照

**Tab 3：团队配置**
* 功能：主编指定、采编人员邀请、校勘员指定、分支负责人指定（V1.5）；权限模板说明
* 说明：配置项目协作团队，分配角色权限

**流程操作**：页面底部显示"推进至内容编排 →"按钮，点击后项目进入阶段 2。（注：人物数据录入通过"信息管理"菜单随时进行，不作为独立流程阶段。项目启动后直接进入内容编排。）

#### 前台页面 05：信息管理（日常管理区，始终可用）

**页面定位**：常态化人丁数据管理的核心入口，不依赖修谱项目状态。用户随时可新增人员、维护亲属关系、设置字辈，实现"实时更新人丁"。修谱流程中的人物数据操作也统一在此完成。

**页面结构**：左侧子菜单切换三个子模块（子菜单形式，非 Tab 栏）

**子菜单 1：人员列表**
* 布局：顶部搜索栏+筛选+新增/批量导入/AI OCR按钮 + 人物列表表格 + 分页 + 回收站入口
* **全局搜索**（v3.1新增）：搜索栏支持按姓名/字号/字辈/世代/人物编号快速搜索，结果高亮匹配关键词，点击直接跳转人物详情。MVP 一期目标 500 人内，搜索为效率工具；大规模族谱为 V2+ 场景。
* 筛选条件：姓名、字辈、世代、性别、在世状态、录入时间、所属修谱/续修项目
* 可操作功能：新增人物（完整支持讳、字、号、行第、字辈、生卒、籍贯、墓葬、传记）；编辑人物、查看详情、删除人物（删除后移入回收站，额度在回收站期满或彻底删除后释放）；批量导入/导出（权限受控、状态受控）；AI老谱OCR识别入口（拍照/上传老谱扫描件，AI识别后校对确认入库）；设置人物隐私级别；回收站（查看已删除、单条/批量恢复，恢复时校验额度）
* 拦截规则（分场景）：额度用尽时隐藏新增、导入、AI OCR按钮，保留编辑、查看；订阅过期时隐藏全部操作按钮，仅保留浏览查看；两种场景均禁止批量导出

**子菜单 2：关系图谱**
* 核心能力：解决传统家谱复杂关系，支持多父、兼祧、出继、嗣子、赘婿
* 功能入口：在人物详情中直接操作绑定关系；也可在此子菜单全局查看和管理
* 功能：为指定人物绑定关系（生父/嗣父/兼祧父/继父/义父/母亲/配偶/赘婿/出继）；自动生成常规双向关系，特殊关系人工确认留存备注；查看某人全部亲属关系清单、关系备注溯源、修改记录；以图谱形式可视化展示全族关系结构
* 可视化优化：支持按分支筛选、按世代折叠；超过3000人时自动降级为"折叠+分代渲染"（虚拟渲染+二分查找定位）
* 说明：从原"亲属关系"+"世系图"两个 Tab 合并为统一的"关系图谱"子菜单，既有结构化关系管理，也有可视化图谱展示

**子菜单 3：字辈列表**
* 功能：录入本族谱字辈诗、设置起始世代，全局适配所有修谱、续修项目；以列表形式展示各世字辈对照
* 自动校验：新增人物、续修增补人物自动匹配世代、校验字辈是否合规。**字辈不匹配的处理方式统一为"可存 + 存疑"**：弹窗提示字辈与字辈诗不匹配，用户可选择"仍保存（标记存疑）"或"修改后保存"。不硬拦截提交，但存疑记录在人物详情中标注，供校对阶段复核。仅硬错（如世代号超出字辈诗范围）才拦截提交。

> **信息管理区定位说明**：信息管理为日常管理区菜单，不包含流程推进/回退按钮。人物数据录入与修谱流程解耦——用户可在任何时间新增人员、维护关系，修谱流程的内容编排阶段通过引用信息管理中的人员数据完成谱书编排。

#### 前台页面 06：内容编排（阶段 2）

**页面定位**：主编整合已采集数据、撰写谱文、规整世系、完成初审的工作台。

**页面结构**：顶部 Tab 栏切换三个子模块

**Tab 1：谱书章节**
* 功能：管理谱序、凡例、家训、祠堂记、艺文、传记等独立文本章节，支持富文本编辑、排序、备注溯源
* 家族文化联动：姓氏源流、堂号起源等内容在"家族文化"页面录入，在此 Tab 中自动映射为谱书章节（姓氏源流→谱序篇，堂号起源→堂号篇），支持微调排版位置
* 续修适配：续修项目可继承历史章节，支持增补新序、新艺文、新修谱后记

**Tab 2：世系规整**
* 功能：世系图预览（只读模式）、关系完整性检查、缺失数据提示（如某人物无父、无生卒等异常标红）、数据统计概览
* 说明：主编在此审视全族数据完整性，决定是否需要前往"信息管理"菜单补充数据

**Tab 3：初审检查**
* 功能：系统自动扫描全部人物与章节，生成初审检查清单（缺失字段、异常关系、敏感词命中、逻辑冲突初筛）；主编逐项确认或标记待整改；初审通过后可推进至校对

**流程操作**：页面底部显示"推进至校对 →"按钮和"← 回退至项目启动"按钮。**v3.1.2 门禁：人物数=0 时"推进至校对"按钮置灰禁用**，并提示"请先录入至少 1 位族人"。广录族人行动卡在人物数为 0 时高亮提醒。

#### 前台页面 07：校对（修谱流程区，阶段 3）

**页面定位**：校勘员专项勘误、批注、疑点复核、驳回整改的工作台。支持协同校对——邀请各分支负责人参与本支人员信息校对（**校对邀请功能为 V1.5 上线，MVP 标准模式由拥有者代行校勘员职责**）。

**页面结构**：左侧子菜单切换三个子模块

**子菜单 1：人员列表**
* 功能区：待校对数据自动归集（人物、关系、谱文、章节）；展示各人员校对状态（待校对/校对中/已通过/存疑/驳回）；专项校对操作（勘误批注、疑点标记、内容修正、通过校验、驳回重编）；校对痕迹永久留存；批量校对；校对进度可视化
* **流程锁说明**（v3.1.2 修正，v3.1.6 对齐权威规则）：校对锁定的范围是项目级数据（章节、排版参数），**族谱级活数据（人物、关系）仍可通过日常管理区"信息管理"修改**。**校对直接对活数据进行，MVP 不设项目级人物快照。校勘员在校对-人员列表中看到的是活数据当前状态。核心规则：当 `current_stage ∈ {3, 4}`（校对或排版）时，任何对已标记 review_status=1（通过）的人物的修改，系统自动将其 review_status 重置为 0（未审核），需重新校对（排版期改人后标准模式回校对终审，简易模式见排版页内一键确认）。** 如需冻结人物数据供校对，主编可手动"快照锁定"（高级功能，V1.5）

**子菜单 2：校对邀请**（V1.5 上线，MVP 中隐藏入口并标注"V1.5 开放"）
* 功能：主编/拥有者向各分支负责人发起校对邀请，分配校对范围（按分支、按世代、按人员范围），设定校对截止时间
* 邀请流程：选择分支负责人 → 指定校对范围 → 设定截止时间 → 发送邀请 → 被邀请人收到通知 → 接受/拒绝 → 进入校对人员列表开展工作
* 协同规则：每位被邀请的分支负责人仅可校对自己分支范围内的人员信息；校对结果提交后由主编/校勘员终审
* 说明：实现"分支自治校对 + 主编终审"的协同模式，降低主编逐一校对全族数据的工作量

**子菜单 3：审核结果**
* 功能：整合原"疑点台账"与"审核记录"。展示全部校对与审核操作记录（操作人、时间、修改前后对比、备注），全程溯源；归集所有标记为"存疑"的人物与内容，支持逐条复核、补充考证、解除存疑或确认归档
* **逻辑冲突检测报告**（v3.1新增）：系统自动执行全量逻辑冲突检测，生成冲突检测报告，展示年代冲突、断代缺失、重复人物、关系异常、字辈不匹配等问题，支持逐条处理
* 存疑归档上限：存疑人物数 ≤ 总人物数的 5%，每条必须填写存疑原因与考证备注

**终审放行标准**：系统自动校验（无未处理疑点+无未处理逻辑冲突）+ 主编人工终审双校验通过，方可进入智能排版环节。

**权限**：校勘员仅可校对批注；主编可终审复核、流程驳回；采编仅可查看整改；拥有者最高终审；分支负责人仅可校对本支范围数据。

**流程操作**：页面底部显示"推进至智能排版 →"按钮（需终审通过）和"← 驳回至内容编排"按钮。

#### 前台页面 08：智能排版（修谱流程区，阶段 4）

**页面定位**：智能排版、版式锁定、PDF导出的工作台，校对终审通过后进入此阶段。

**页面结构**：顶部 Tab 栏切换三个子模块

**Tab 1：智能排版**
* 功能：四大传统家谱版式切换（苏式垂丝、欧式分栏、宝塔式、牒记式）；版式预览；手动微调（单段对齐、特殊字符适配、自定义换行）
* 续修适配：续修项目可继承旧版排版样式、自动衔接历史页码与版式规范，也可重置新版版式

**Tab 2：版式锁定**
* 锁定前：可修改内容、可微调版式、页码自动实时刷新
* 锁定后：禁止一切内容修改，仅可微调版式样式，杜绝内容变动导致页码错乱
* 锁定后如需改内容，必须回退至校对环节、解锁版式、重置页码
* **活数据变更门禁**（v3.1.2 新增，v3.1.4 收紧路径 B，v3.1.5 补充简易模式）：版式锁定后，若日常管理区修改了人物活数据（增删改人物），系统自动标记排版为"脏"状态（Project.layout_dirty=1）——PDF 预览标红提醒"活数据已变更，排版需刷新"。此时**禁止 PDF 导出**。v3.1.4 核心：排版期改人/改关系同样触发 review_status 重置（与校对期一致），因此解除脏状态后仍须满足 review_status 全量通过：
  - **路径 A（推荐，标准模式）**：回退至校对，重新终审通过后再回到排版——确保所有变更经过校对确认
  - **路径 B（快速刷新，标准模式）**：手动"刷新同步"（重新拉取活数据重排），刷新清脏标记（layout_dirty=0），但**路径 B 等同路径 A 的终审要求**——系统仍校验全量人物的 review_status，若存在 review_status=0（未审核）或 review_status=3（待整改）的人物（存疑归档 review_status=2 除外），**仍禁止 PDF 导出**，必须回到校对处理后方可导出
  - **简易模式**（v3.1.5 新增）：简易模式无校对菜单，不要求"回校对终审"。改为排版页内弹出"活数据已变更"确认弹窗，拥有者点击"确认纳入"后系统批量将变更人物 review_status 置为 1，清脏标记后可导出。弹窗展示变更人物列表，支持逐条查看
* 目录、页码定稿后自动静态固化，不再随内容变动刷新

**Tab 3：PDF导出**
* 功能：印刷版PDF生成与下载；成册保存
* GEDCOM导出（V1.5）：国际通用家谱数据格式导出，便于跨平台迁移

**商业化拦截规则**：订阅过期、额度用尽状态下，禁止版式锁定、禁止定稿、禁止PDF印刷导出、禁止成册保存，仅可预览。

**权限**：仅有效订阅状态下的拥有者、主编可操作排版、定稿、印刷PDF导出。

**流程操作**：页面底部显示"推进至发布归档 →"按钮（需版式锁定完成）和"← 回退至校对"按钮。

**四大传统版式详细规格**

**版式一：苏式垂丝图**
* 起源与特点：北宋苏洵所创，世代为经、父子垂直线为纬，形如垂挂丝线，是传统家谱最常见的世系图样式
* 布局结构：从上至下按世代排列，同代人物按长幼从左到右排列；父子间以竖直线（"丝"）连接；配偶并列于夫侧用横线连接
* 排版规则：世代间距24pt；人物间距最小20pt；信息框标准80pt×36pt；垂直线0.5pt深灰；分页在整代之间，不得拆分一代人；跨页标注"接前页第X代"
* 特殊情况处理：无子（无线标注"无传"）；多子（垂丝分岔连接各子）；兼祧（双垂丝+标注）；出继/嗣子（虚实线区分+标注）；多妻（正妻居右依次向左，妾用虚线）；女性（细边框/不同底色区分，出嫁女垂丝止于本身）

**版式二：欧式分栏**
* 起源与特点：北宋欧阳修所创，表格形式，世代分行人物分栏，由右向左递进（古法尚右），便于查阅上下代关系
* 布局结构：从右至左按世代排列，每栏一代；同一世代人物从上到下按长幼排列；上下代间用横线连接
* 排版规则：栏宽120pt可微调；行高40pt；连接线0.5pt；每栏顶部标注世代数；横向分页标注"前接第X世"；纵向分页标注"接前页第X世第X人起"
* 特殊情况处理：无子（空格标注"无传"）；多子（父格底部分多条横线）；兼祧（同一人物格+角标"兼祧"）；出继（本生父旁标注+嗣父格中列入）；配偶（夫格内记述，不单列格）

**版式三：宝塔式**
* 起源与特点：始祖为塔顶，子孙逐层展开，形如宝塔，直观展示家族树状结构，适合中小家族（200人以内）整体一览
* 布局结构：顶部居中为始祖；第二代左右对称展开；逐级加宽形成下宽上窄的宝塔形；父子间用斜向/纵向连接线
* 排版规则：节点直径40-50pt（圆形/圆角矩形）；层级间距60pt；同级间距最小30pt；连接线0.75pt；居中对称分布；字体始祖16pt逐层递减至最小10pt
* 特殊情况处理：无子（无分支线）；多子（长幼从左到右对称排列，奇数时正中对父）；兼祧（双线连两父+标注）；出继（虚实线+标注）；配偶（并列夫右侧，横线连接，尺寸略小/异色）；女性（不同形状/边框色区分）

**版式四：牒记式**
* 起源与特点：以人物传记为主体，按世代长幼逐条排列，每人一篇小传（"牒"），世系关系通过文字说明体现，是内容最详实的谱书格式
* 布局结构：按世代顺序排列；每世内按长幼排列；每人一条目，含标题（姓名+字号）和正文（传记）；世系关系在条目中用文字说明
* 排版规则：条目标题姓名三号黑体+字号小四宋体；条目间距空1行，首行缩进2字符；正文五号宋体1.5倍行距；每世前有"第X世"大标题；尽量避免条目中间分页；谱书前有人名目录按世代索引
* 特殊情况处理：无子（标注"无嗣"或"女一，适某"）；多子（按长幼列出"生子五：长某、次某…"）；兼祧（本生条目标注"出继与某公为嗣，兼祧本生"）；出继/嗣子（出继方与嗣父方条目各标注说明）；信息不详（标注"生卒未详""葬地失考"等，保留条目位置）

#### 前台页面 09：发布归档（阶段 5）

**页面定位**：五步流程最终闭环环节，完成版本封存、公示、归档，为后续续修提供基准版本。

**页面结构**：顶部 Tab 栏切换四个子模块

**Tab 1：归档操作**
* 定稿版本封存：智能排版完成后，可执行发布归档操作，系统自动将当前项目版本标记为【正式归档版本】，纳入族谱永久正史版本库，锁定所有数据禁止篡改
* 谱书公示配置：支持自定义归档谱书公示范围，可选全网公开、仅族内成员可见、完全私密归档
* 归档台账留存：自动记录每一次归档信息（修谱批次、归档时间、操作人、定稿版式、总页数、人物总数、增补内容概况）
* 续修基准绑定：归档完成后，该版本自动设为「下一期续修基准版本」
* 归档后权限锁定（v3.1.3 修正）：**只锁定已归档项目的项目级数据**（章节、排版参数、版本快照不可篡改），仅保留项目级数据的预览、对比、导出权限。**日常管理区不受影响**——归档后仍可通过信息管理新增/编辑人物（活数据继续演进，标记 is_changed_since_archive）、录入家族文化、管理权限

**Tab 2：版本快照**
* 功能：查看所有定稿版本快照，记录版式参数、成册内容、修订记录、审核台账
* 规则：所有版本永久留存、不可删除、不可篡改；支持回溯、下载

**Tab 3：版本对比**
* 功能：新旧版本全方位对比——人物增减、关系变动、谱文修改、批注差异、版式变更、章节增补、附件变动全维度比对
* MVP 状态：V1.5 上线，MVP 中隐藏入口

**Tab 4：续修发起**
* 功能：基于当前归档版本，快速发起下一期续修项目
* 续修规则（v3.1.3 修正）：新建续修**不从归档快照恢复人物/关系**——活数据始终是同一套（genealogy_id 下的 Person/Relationship 表）。续修继承的是项目级数据（章节从快照复制为新一期初始章节、版式参数继承/重置可选、批注继承/清空可选）；历史版本永久只读封存；支持N期续修
* **续修增补清单**（v3.1新增）：发起续修时，系统自动对比「上一归档版本」与「当前日常管理活数据」之间的差异（基于Person.is_changed_since_archive字段），生成"续修增补清单"（新增人物、修改信息、新增文化内容等），主编可逐项确认是否纳入本次续修项目，避免日常零散变动影响谱书的严肃性
* 续修创建拦截：账号过期、额度用尽、租户冻结时禁止新建续修项目
* MVP 状态：V1.5 上线，MVP 中隐藏入口不做功能开发（数据模型已预留）

**操作权限**：仅拥有者、主编可执行归档操作；归档后不可回退编辑，仅可新建续修；过期/额度不足禁止归档。

> **归档与日常管理的关系（双区架构核心规则）**：
>
> 归档封存的是「修谱项目的当期定稿快照」，不是锁死整个族谱。日常管理区操作的是族谱的「活数据」，归档后依然可以继续新增人员、更新关系、录入文化内容。
>
> | 数据层面 | 归档前 | 归档后 | 续修时 |
> |---------|-------|-------|-------|
> | 日常管理活数据 | 可读写 | **继续可读写** | 活数据中的变更作为"待纳入内容" |
> | 修谱项目数据 | 可读写（受流程锁限制） | 只读封存，版本永久留存 | 从归档版本创建新项目快照 |
>
> 这样设计确保了两个核心价值的共存：①修谱版本的严肃性与不可篡改性（每一期谱书定稿后永久封存）；②家族人丁的实时可管理性（不用等下一次修谱才能记录新出生、新嫁娶等变动）。

#### 前台页面 10：家族文化

**页面定位**：家族文化内容的统一管理入口，横切于五步流程（任何阶段都可录入和查看）。家族文化是族谱区别于普通人物名录的核心价值——它承载的是家族的精神传承、历史脉络和文化记忆，而非单纯的世系数据。

>
> **v3.1 Tab 顺序调整**：MVP 期间将家规家训和家族大事记排在前面（Tab 1、Tab 2），姓氏源流和堂号起源排在后面（V1.5开放后恢复传统顺序）。

**页面结构**：顶部 Tab 栏切换五个子模块（MVP 仅显示前两个）

**Tab 1：家规家训**（MVP）
* 布局：家规家训条目列表 + 新增/编辑条目弹窗
* 功能：以结构化条目形式管理家规家训，支持分类（祖训/家规/家训/族规/戒律）、排序、富文本内容
* 条目字段：标题、分类、内容（富文本）、出处（某代祖某公立）、排序号
* 说明：家规家训是家族精神传承的核心载体，不同于普通章节，需要结构化管理以便在智能排版时按分类和顺序自动生成家训篇章
* 续修继承：续修时可继承历史家规，也可增补新订家训

**Tab 2：家族大事记**（MVP）
* 布局：时间轴视图 + 列表视图双模式切换 + 新增/编辑事件弹窗
* 功能：以时间轴形式记录家族重大事件，支持按年代、事件类型筛选浏览
* 事件字段：事件日期（支持农历/公历文本）、事件类型（修谱/祭祀/迁徙/婚嫁/丧葬/科考/封赠/灾荒/建祠/其他）、事件标题、事件描述（富文本）、关联人物（可关联族谱中的人物）、关联附件（图片等）

* 列表视图：表格形式，支持筛选、排序、导出
* 续修继承：续修时自动继承历史大事记，可在时间轴末尾继续增补新事件

**Tab 3：姓氏源流**（V1.5）
* 布局：富文本编辑器 + 结构化字段区
* 功能：记录本家族姓氏的起源、得姓始祖、历代迁徙路线、郡望堂号沿革
* 结构化字段：姓氏、得姓始祖、发源地、郡望、历代迁徙路线（时间 + 地点 + 原因，支持多条）
* 富文本区：详细叙述姓氏起源故事、历史名人、姓氏考辨

* 功能：记录本族堂号的名称、来历典故、所属郡望、与同姓其他堂号的关系
* 结构化字段：堂号名称、别称、来历类型（地名/典故/先祖事迹/皇帝赐封）、关联郡望
* 富文本区：详细叙述堂号起源故事、堂联、堂号文化内涵

* 功能：家族公共相册，区别于人物个体照片——记录家族集体活动、祠堂祖宅、族谱老照片、家族聚会等

## 第五部分：非功能性需求

### 5.1 性能要求

| 场景 | 指标 | 说明 |
|------|------|------|
| 页面加载 | 首屏 ≤ 2秒 | 所有页面首屏渲染时间（不含图片加载） |
| 人物列表查询 | ≤ 500ms | MVP 500 人级分页查询；远期容量目标万人级（V2+） |
| 人物全局搜索 | ≤ 300ms | 按姓名/字号/字辈搜索，结果实时返回（v3.1新增） |
| 世系图渲染 | ≤ 3秒 | 3000人级世系图首次渲染（支持折叠+分代虚拟渲染） |
| 关系图谱交互 | ≤ 200ms | 展开/折叠节点响应时间 |
| 批量导入 | ≤ 5秒 | 1000行Excel导入校验+入库 |
| AI老谱OCR识别 | ≤ 30秒/页 | 单页老谱扫描件识别处理（Spike 验证项，非 MVP 硬指标） |
| 逻辑冲突检测 | ≤ 10秒 | MVP 500 人级全量检测；远期容量目标万人级（V2+） |
| PDF生成（500人内） | ≤ 30秒 | 牒记式PDF生成 |
| PDF生成（500-2000人） | ≤ 2分钟 | 含目录、页码、分页 |
| PDF生成（2000人以上） | ≤ 5分钟 | 建议分卷导出 |
| 并发编辑锁检测 | ≤ 100ms | 编辑锁状态实时检测 |
| 版本快照生成 | ≤ 30秒 | 归档时全量快照写入 |

### 5.2 兼容性要求

* 浏览器：Chrome 90+、Firefox 88+、Safari 14+、Edge 90+
* 屏幕分辨率：最低 1280×720，推荐 1920×1080
* 移动端适配：响应式布局，适配 768px 以上平板（MVP不做手机端原生适配）
* 微信小程序：轻量浏览版（**V1.5 上线**，支持查看世系图和人物详情，不支持编辑。v3.1.2 修正：原标注"MVP末段上线"与 §0.3.3 范围声明矛盾，统一降为 V1.5）
* 文件格式：Excel导入支持 .xlsx/.xls，PDF导出支持 A4/A3/16开

### 5.3 安全要求

* 传输加密：全站 HTTPS，API 请求签名验证
* 存储加密：敏感数据（手机号）数据库加密存储
* 文件安全：上传文件经病毒扫描后入库，可疑文件隔离并通知后台审核（v3.1新增）
* 权限隔离：严格租户隔离，协作成员通过 Collaborator 表关联，不改变自身 tenant_id
* SQL注入防护：所有数据库查询参数化，禁止字符串拼接
* XSS防护：富文本内容入库前过滤危险标签，展示时转义
* CSRF防护：所有写入操作携带 CSRF Token
* 接口限流：登录接口 5次/分钟，注册接口 3次/分钟，AI OCR接口 10次/分钟
* 审计日志：所有关键操作永久留存，不可删除不可篡改
* 数据备份：每日全量备份 + 实时增量备份，备份保留 30 天

### 5.4 可用性要求

* 系统可用性：SLA 99.5%（月度）
* 故障恢复：RTO ≤ 4小时，RPO ≤ 1小时
* 监控告警：接口异常率 > 1% 自动告警，响应时间 > 5秒 自动告警
* 灰度发布：新功能支持灰度发布，按租户ID哈希分流
